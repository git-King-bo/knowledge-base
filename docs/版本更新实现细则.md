# 知识库版本更新提醒实现细则

## 目标与适用范围

让长期打开的页面发现新前端版本，同时避免刷新丢失表单、上传请求或正在生成的回答。
本次实现包括版本产物、检测、提示、操作保护、问答输入草稿，以及发布时保留旧静态资源。
不引入 Service Worker、WebSocket 或新的后端业务接口；不改变既有账号和模型鉴权。

## 1. 版本如何产生与检测

`frontend/vite.config.ts` 在每次生产构建时生成唯一版本，将同一个值编译为 `__APP_VERSION__`，并输出：

```json
{"version":"20261116T030000Z-12345"}
```

静态接口约定：`GET /version.json`，公开只读、无请求体、成功返回 JSON 对象，必需字段 `version` 为非空字符串，仅允许字母、数字、下划线、点和短横线，最长 101 字符。
请求端使用 `cache: no-store`；Caddy 为该路径返回 `Cache-Control: no-store`，并使用独立静态处理器，文件缺失时返回 404，不回退到 SPA 首页。
不包含密钥、用户、数据库信息或部署路径。HTTP 失败、HTML 回退、非法 JSON、无效字段和断网均被忽略。

`deploy/deploy.sh` 把自动产生的版本号传入前端构建：完整 Docker 构建走 build argument，缓存运行环境构建走环境变量。手动 `pnpm build` 则生成随机唯一版本。
前后端独立发版时，仅发布后端不会修改前端镜像和 `/version.json`，因此不会弹出无意义的刷新通知。
开发服务器使用 `development`，不做轮询。

`frontend/src/lib/versionCheck.ts` 负责检查：

- 页面可见且联网时，每 60 秒检查一次；启动、回到标签页、恢复网络时立即补查。
- 同一时刻最多一个请求，8 秒超时；组件卸载时终止请求并停止定时器。
- 新版本与当前页面内嵌版本不同则提示，不比较时间或大小，因此回滚到较早版本也能被发现。
- 断网和暂时的发布错误不触发刷新、不清除用户输入。

为什么这样做：一分钟内提醒足够覆盖日常发版，静态小文件不需要增加长连接和后端状态。版本必须在构建时内嵌，不能把第一次网络查询当当前版本，否则部署完成后才首次查询的旧页面会漏报。

## 2. 提示与更新时机

`UpdateNotice.vue` 在应用根部显示固定的小型提示，不抢焦点、不自动刷新：

> 新版本已发布　立即更新　稍后

“稍后”只在当前页面生命周期内隐藏同一候选版本；出现其他版本会再次提示。刷新页面后使用最新版本。
“立即更新”会实时检查状态，不能仅依赖打开提示时的状态，因为用户可能随后开始上传或提交。

| 状态 | 行为 | 原因 |
| --- | --- | --- |
| 没有修改、没有进行中的操作 | 用户点击后刷新 | 操作由用户明确触发 |
| 有未保存表单 | 展示来源，提供返回保存或明确放弃后更新 | 不擅自提交业务数据，也不猜测哪个接口代表保存 |
| 只有未发送的问答/检索输入 | 可保存输入草稿并更新，也可明确放弃 | 输入结构固定，可安全限定缓存字段 |
| 正在上传、提交、检索或生成回答 | 禁止刷新；可选择完成后更新 | 刷新会取消浏览器请求，提交结果可能变得不确定 |
| 操作完成，但仍有未保存内容 | 继续等待，不自动刷新 | “完成”不等于所有内容都已保存 |
| 后台任务已成功提交 | 请求结束后可以更新，刷新后重新查询任务 | 后台任务由服务器持久化执行，不依赖当前页面 |

直接点击浏览器刷新或关闭时，若有未保存内容/进行中的操作，注册的 `beforeunload` 会请求浏览器显示原生确认。它只是补充保护，浏览器不保证所有场景都会展示，不能当可靠的保存机制。

## 3. 如何知道页面是否安全

`frontend/src/lib/updateSafety.ts` 提供组件级守卫，每个守卫报告 `dirty()`、可选 `busy()` 和可选 `saveDraft()`。
守卫在组件销毁时移除；KeepAlive 中的问答/检索输入继续参与检查，因为切换菜单不应让尚存于内存的输入被忽略。
`useFormUpdateGuard` 在每次打开编辑界面时记录初始快照，比较实际修改；仅打开弹窗不会误判为修改。

已接入范围：

- 知识库新增/编辑表单。
- 模型配置表单，包括密钥修改；只在内存中比较，绝不缓存表单。
- 人才资料编辑与保存请求。
- 问答、检索输入和会话持久化；会话保存失败也算未保存状态。
- 登录输入与请求；账号、密码和授权管理表单及请求。
- `useTask` 的所有操作，包括上传、提交和流式回答，通过全局活动任务计数保护。

为什么使用组件状态：单纯监听 DOM 输入事件无法可靠判断保存是否成功、值是否恢复原样，也覆盖不到隐藏的 KeepAlive 页面、程序更新和异步提交。
新增编辑页面或不通过 `useTask` 执行的长任务，需要显式注册守卫，否则无法自动推断其安全性。普通筛选条件没有被全部当作业务表单缓存。

## 4. 草稿如何保存及安全边界

`updateDraft.ts` 只允许保存 `{schema, question, savedAt}`，不序列化整个表单、用户、请求、模型配置或会话对象。
使用当前标签页的 `sessionStorage`，key 按用户 ID 和 chat/retrieval 模式隔离。读取时校验结构、长度和时间，最长保留 24 小时，恢复后消费一次。

- 仅在用户点击“保存问答草稿并更新”时写入。
- 存储被禁用、配额不足或写入失败时，不刷新，提示返回保存。
- 恢复后显示说明，提醒核对知识库和模型后再发送，避免自动在错误上下文发起请求。
- 密码、API Key、文件内容、模型回答和聊天历史不进入该草稿缓存。
- 当前聊天历史依赖既有服务器会话保存，刷新后可以从历史中打开；此功能不恢复被取消的模型连接，也不恢复文件选择。

sessionStorage 只是同源脚本可访问的临时存储，不是加密保险箱。问答输入本身可能包含业务信息，因此不跨标签共享、不长期保存，也不自动存所有内容。

## 5. 发布与旧资源

`compose.company.yaml` 为前端增加只读 `/srv/assets` 挂载，对应服务器 `data/frontend-assets`。
`company-apply.sh` 在前端/全量发布时：

1. 从现有前端容器复制旧 assets，兼容首次从旧部署切换。
2. 从新镜像的临时容器复制新 assets；失败则不继续切换。
3. 启动新版前端，HTML 和版本信息来自新镜像，带内容哈希的 JS/CSS 从累积资源目录读取。

为什么保留：提醒出现后用户可能选择继续操作，旧页面仍可能请求旧 JS/CSS。立即删除旧文件会让“稍后更新”失效。
目前旧 assets 不自动清理，需监控磁盘；可以在以后明确支持的旧版本窗口后再制定清理策略。目录仅由发布工具写入，不与业务上传目录共用，不保存密钥。

原有备份、健康检查及配置回退逻辑继续保留。旧的回退配置没有 assets 挂载时按旧方式运行。

## 6. 部署和启用

```sh
bash deploy/deploy.sh frontend  # 只发布本次前端更新功能
bash deploy/deploy.sh           # 有前后端联动修改时全量发布
```

本次未新增后端 API，不需要数据库迁移。发布操作仍会按已有流程更新服务器配置。
首次上线后，早已打开的旧页面没有检测代码，需要用户先手动刷新一次；之后打开的页面才具备自动提醒能力。

验收时先打开版本 A 并输入内容，再发布版本 B；不要先刷新页面，否则无法验证旧页面检测新版本。可通过切换标签页再返回立即触发检查。

## 8. 不应误解为已解决的问题

版本提示不能实现跨版本 API 兼容。后端仍应尽量兼容短时间运行的旧前端，破坏性契约变更需要独立迁移安排。
浏览器不刷新也无法避免后端容器重启终止 SSE；已有停止宽限和后台任务机制不能等同于模型请求断点续传。
“发现新版本”也不保证它与所有旧数据兼容，服务端权限、输入校验和迁移验证仍是独立职责。
